# 数据链路层：服务与成帧

> 来源：第 3 章课件 PDF 第 4—20 页；`note3.pdf` 第 1 页。衔接：[分层与封装](../week1.md)。

## 1. 从比特流到帧

物理层负责传输比特；数据链路层在一段链路的相邻节点之间组织帧，并向网络层提供服务。局域网体系中常划分逻辑链路控制 LLC 与介质访问控制 MAC 子层，不宜把这种划分机械套用到所有点到点协议。

| 功能 | 要解决的问题 | 常见机制 |
| --- | --- | --- |
| 成帧 | 一帧从哪里开始、在哪里结束 | 长度、定界符、填充 |
| 差错控制 | 位错误、丢失、重复等 | 检错、纠错、确认与重传 |
| 流量控制 | 发送速度超过接收方处理能力 | 停等、窗口、反馈或限速 |
| 介质访问控制 | 多个站争用共享介质 | 具体 MAC 机制，后续局域网内容 |

这是链路层可能提供的功能集合，**不是每个链路层协议都实现全部功能**。例如基本 PPP 检错但不通过数据帧重传提供可靠交付。

流量控制主要保护接收方；拥塞控制关注网络中的资源拥塞，两者不能混为一谈。

## 2. 三类服务

| 服务 | 是否先建立逻辑连接 | 是否确认 | 课堂例子或应用条件 |
| --- | --- | --- | --- |
| 无确认无连接 | 否 | 不逐帧确认 | 以太网；误码少或需及时交付 |
| 有确认无连接 | 否 | 对帧确认 | 无线链路；802.11 的典型单播传输 |
| 有确认有连接 | 是 | 使用确认及连接状态 | 要求可靠、有序交付的设计 |

“有确认”不等于“有连接”；“无确认”也不意味着没有 CRC。差错检测回答帧是否可能损坏，确认机制回答对方是否收到，连接则涉及通信前后的状态管理。

## 3. 帧与分组

```text
网络层：                   [网络层分组]
链路层： [帧首部 |          有效载荷          | 帧尾]
物理层：              编码并发送比特流
```

网络层分组常作为帧的有效载荷。帧首部、帧尾可以携带控制字段与校验信息，但具体字段由协议决定，不是每种帧都使用相同格式。

成帧的两个关键目标是：

1. **定界**：接收端能区分帧的起止。
2. **透明传输**：数据中即使出现与定界符相同的内容，也能无歧义传输和恢复。

## 4. 四种成帧方法

### 字节计数法

用长度字段表示帧长。课件例子把计数字节本身也算入帧长：`5 1 2 3 4` 共 5 字节。做题要先确认长度是否包含首部。

风险是计数字段一旦出错，后续边界也可能整体错位。它不是“只能在无错信道使用”，而是单独依赖计数恢复同步比较脆弱，实际设计可结合其他机制。

### 带字节填充的定界符法

用 FLAG 标识边界，用 ESC 转义数据中的特殊字节。对于课件的简化规则：

```text
原始载荷： A FLAG B ESC
填充载荷： A ESC FLAG B ESC ESC
完整帧：   FLAG [首部、填充载荷、尾部] FLAG
```

接收端在载荷解析中遇到 ESC，就把其后一个字节当作数据，不将它解释成控制字符；遇到未转义的 FLAG 才判为边界。不同协议转义规则不同，PPP 还会异或 `0x20`，见[第六篇](06-ppp-and-pppoe.md)。

### 带比特填充的定界符法

典型 FLAG 为 `01111110`。在受填充处理的帧内容中，每出现连续 5 个 1，就插入一个 0；FLAG 本身不填充。

```text
原始数据：0 11111 1 0
填充结果：0 11111 [0] 1 0  （方括号标出新插入的位）
实际位串：011111010
```

读取填充后的位串，连续读到 5 个 1 后，若下一位为填入的 0 就删除。识别完整 FLAG 和非法序列属于成帧状态机的工作；不能把“看到第六个 1”单独当作合法帧结束的充分条件。

**操作顺序：先计算 FCS，再做透明传输填充；接收端先去填充，再校验 FCS。**PPP 的 HDLC 类成帧还会对相应首部及 FCS 内容做填充，不只是对用户数据操作，见 [RFC 1662 §4.2、§5.2](https://www.rfc-editor.org/info/rfc1662/)。

### 物理层编码违例

在正常数据编码不会使用的码型或信号模式中选择控制标记。例如冗余块编码中有些码型保留给控制用途。它依赖特定线路编码，不能对任何编码都凭空找出“永远不会出现在数据中的位串”。

## 5. 差错与流量控制如何接上成帧

| 情况 | 仅靠什么不够 | 还需要什么 |
| --- | --- | --- |
| 帧中某些位翻转 | 帧边界正确不代表内容正确 | 检错码或纠错码 |
| 整帧丢失 | 收不到内容，CRC 无从校验 | 超时与重传 |
| ACK 丢失后数据重传 | 重传可能带来重复 | 序号与重复检测 |
| 后续帧先到 | 每帧都正确也可能次序错误 | 序号、缓存与按序交付策略 |
| 接收方处理太慢 | 位级差错检测不能保护缓冲区 | 流量控制 |

检错、确认、定时器与序号各自解决不同问题；把它们组合起来才形成后续的可靠传输协议。

## 自测与答案

1. 数据里含 FLAG 是否意味着不能传？**可以传，按协议做填充或转义。**
2. 比特串 `111111` 填充后是什么？**`1111101`，第 5 个 1 后插入 0。**
3. 一帧 CRC 正确但重复到达，靠 CRC 能拒绝重复吗？**不能，需要序号与接收状态。**
4. 每一层都必须可靠传输吗？**不是，各层按其协议提供不同服务。**
5. 哑确认帧是否意味着物理链路只需单向？**不是，ACK 仍需反向通路。**
